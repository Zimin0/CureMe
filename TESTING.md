# Тесты CureMe

Тесты разложены по уровням «пирамиды тестирования»: внизу много быстрых проверок отдельных функций, наверху несколько медленных сценариев в настоящем браузере.

```
                  ▲  docker smoke   образ как на сервере отвечает на запросы        (CI)
                 ▲▲  e2e            Playwright: Chromium + настоящий бэкенд, 9 сценариев × ПК и телефон
               ▲▲▲▲  компоненты     React-страницы с поддельным API (MSW)
             ▲▲▲▲▲▲  интеграция     FastAPI + настоящая база, все эндпоинты и права доступа
           ▲▲▲▲▲▲▲▲  миграции       Alembic: схема из миграций совпадает с моделями
         ▲▲▲▲▲▲▲▲▲▲  unit           чистые функции: коды, подбор, JWT, остатки, даты
```

| Уровень | Где лежит | Инструменты | Сколько |
|---|---|---|---|
| Unit (бэкенд) | `backend/tests/unit/` | pytest, Hypothesis | 134 |
| Интеграция API | `backend/tests/integration/` | pytest, FastAPI TestClient, SQLite/Postgres | 255 |
| Миграции | `backend/tests/migrations/` | Alembic autogenerate | 4 |
| Unit и компоненты (фронтенд) | `frontend/src/**/*.test.ts(x)` | Vitest, Testing Library, MSW, jsdom | 113 |
| End-to-end | `frontend/e2e/` | Playwright | 9 × 2 устройства |
| Smoke образа | `.github/workflows/tests.yml` | Docker, curl | 1 |

Покрытие кода бэкенда тестами: 98 %.

## Как запустить

```bash
# бэкенд: все уровни (≈20 с)
cd backend
pip install -r requirements-dev.txt
pytest                        # всё
pytest -m unit                # только unit
pytest -m "not migrations"    # всё, кроме миграций
pytest --cov=app              # с отчётом о покрытии

# те же тесты на Postgres
CUREME_TEST_DATABASE_URL=postgresql+psycopg://cureme:cureme@localhost/cureme_test pytest

# фронтенд
cd frontend
npm test                      # unit + компоненты
npm run test:watch            # перезапуск при сохранении файла
npm run test:coverage

# e2e: нужен собранный фронтенд и Python с зависимостями бэкенда
npm run build
npx playwright install chromium          # один раз
npm run test:e2e                         # сам поднимет бэкенд на :8765 с чистой базой
npx playwright test --ui                 # посмотреть сценарии глазами
PYTHON=../backend/.venv/bin/python npm run test:e2e   # если зависимости в venv
```

На каждый pull request GitHub Actions запускает всё это в workflow **Tests** (`.github/workflows/tests.yml`). Деплой (`deploy.yml`) от него не зависит.

## Что проверяется

**Бэкенд, unit**
- `test_codes.py` — разбор EAN-8/13, GTIN-14, DataMatrix «Честного знака»: разделители GS в любом виде, префиксы сканеров, срок «00» = конец месяца, битые даты, мусор на входе. Property-based тесты генерируют сотни случайных кодов.
- `test_search.py` — нормализация, «стемминг», синонимы («болит голова» → «мигрень»), порог совпадения.
- `test_security.py` — bcrypt, JWT: истёкший, чужой ключ, другой алгоритм, атака `alg=none`.
- `test_services.py` — статус лекарства (ok/low/out/expiring/expired) на границах и списание по FEFO.
- `test_websearch.py` — разбор заголовков аптек, голосование, переход на запасной поисковик.

**Бэкенд, интеграция**
- `test_auth.py`, `test_families.py`, `test_categories.py`, `test_medicines.py`, `test_assist.py`, `test_files.py`, `test_admin.py` — все эндпоинты, включая ошибки валидации и крайние случаи (последний владелец, выход последнего участника, загрузка SVG вместо фото, обход пути в `/api/media`).
- `test_access_control.py` — матрица прав: каждый из 23 семейных эндпоинтов проверяется для гостя (401), чужого человека (404), участника (403 только на действиях владельца) и для подстановки чужого id; каждый из 15 эндпоинтов админки закрыт для гостя (401) и обычных людей (403) и работает у администратора.
- `test_lookup.py` — справочник товаров с подменой интернета (моки httpx).

**Миграции** — одна «голова», `upgrade head` создаёт все таблицы, схема совпадает с моделями, откат до нуля и обратно.

**Фронтенд** — форматирование, клиент API (токен, ошибки, 401), поле остатка, поле срока годности (OCR подменён), карточка лекарства, маршрутизация и защита страниц, вход/регистрация/приглашение, подбор, список с фильтрами, сканирование с ручным вводом, админка (доступ, порядок и создание категорий).

**E2E** — регистрация и вход; добавить лекарство → принять → подобрать по болезни → экспорт → удалить; главная и фильтры; приглашение второго человека по ссылке в отдельном браузере; сканирование нового и уже известного кода; администратор добавляет категорию, и её видит другая семья. Каждый сценарий идёт на экране компьютера и телефона (Pixel 7).

## Что нашли тесты

- **Тап по подписи «Осталось блистеров» уменьшал количество.** Подпись была `<label>`, а первым элементом внутри неё стояла кнопка «−», и браузер «нажимал» её при клике по тексту. То же с «Таблеток в блистере». Исправлено в `QuantityInput.tsx`, заодно у полей появились доступные имена для скринридеров.

## Словарик для собеседования

**Пирамида тестирования** — правило, сколько тестов какого уровня писать: много дешёвых unit-тестов внизу, меньше интеграционных, совсем немного e2e наверху. *Зачем:* быстрая обратная связь и при этом уверенность, что всё работает вместе. *Плюсы:* тесты быстрые и стабильные, а сломанное место видно сразу по уровню упавшего теста.

**Unit-тест (модульный)** — проверка одной функции в изоляции, без базы, сети и браузера. Пример: `stock_of()` получает заглушки упаковок и возвращает статус. *Плюсы:* миллисекунды на тест, точно показывает место ошибки, служит документацией.

**Интеграционный тест** — проверка, что несколько частей работают вместе: HTTP-слой FastAPI + валидация Pydantic + SQLAlchemy + настоящая база. *Зачем:* unit-тесты не поймают ошибку в SQL-запросе или забытую проверку прав. *Плюсы:* близко к реальности, но всё ещё быстро (секунды).

**E2E-тест (end-to-end, сквозной)** — сценарий глазами пользователя: настоящий браузер кликает по настоящему приложению. *Зачем:* проверить, что фронтенд, API и база стыкуются. *Плюсы:* ловит то, что не видно по отдельности (опечатка в URL, сломанная навигация). *Минусы:* медленнее и капризнее, поэтому их мало.

**Smoke-тест (дымовой)** — самая грубая проверка «включили — не задымилось»: собрали Docker-образ, запустили, `/api/health` отвечает. *Зачем:* не выкатить на сервер образ, который даже не стартует.

**Фикстура (fixture)** — заготовка для теста: свежая база, клиент, зарегистрированный пользователь. В pytest это функция с `@pytest.fixture`, тест просто просит её аргументом (`def test_x(client, owner)`). *Плюсы:* нет копипасты подготовки, каждый тест начинает с чистого листа.

**Параметризация** — один тест прогоняется на таблице входов (`@pytest.mark.parametrize`, `it.each`). *Плюсы:* 30 случаев в 10 строках, в отчёте видно, какой именно вход сломался.

**Mock / stub / fake (подмены)** — замена настоящей зависимости на управляемую. *Stub* возвращает заготовленный ответ (поиск в интернете отдаёт «Ларингобакт»), *mock* ещё и проверяет, как его вызвали (`expect(fetch).toHaveBeenCalledWith(...)`), *fake* — упрощённая рабочая реализация (SQLite вместо Postgres). *Зачем:* тест не зависит от интернета и камеры, работает быстро и одинаково.

**monkeypatch** — фикстура pytest, которая временно подменяет функцию или настройку и сама возвращает всё обратно после теста.

**Dependency override** — подмена зависимости FastAPI (`app.dependency_overrides[get_db] = ...`): приложение то же, но берёт тестовую базу. *Плюсы:* не нужно менять код приложения ради тестов.

**MSW (Mock Service Worker)** — перехватывает `fetch` и отвечает как бэкенд. Компонент ходит в API как обычно и не знает, что сервер поддельный. *Плюсы:* тестируем реальный код запросов, а не заглушку `api()`; неописанный запрос сразу роняет тест.

**Testing Library** — тестирует компоненты так, как их видит человек: ищет кнопку по тексту и роли (`getByRole('button', { name: 'Войти' })`), а не по CSS-классам. *Плюсы:* тесты не ломаются при рефакторинге вёрстки и заодно проверяют доступность (a11y) — так и нашёлся баг с подписью.

**jsdom** — браузерное окружение (DOM, `localStorage`, события), эмулированное в Node. *Плюсы:* компонентные тесты без запуска браузера, в сотни раз быстрее e2e.

**Property-based testing (Hypothesis)** — вместо конкретных примеров описываем свойство («для любого EAN-13 с верной контрольной цифрой парсер вернёт тот же код»), а библиотека сама генерирует сотни входов и при падении ужимает их до минимального примера. *Плюсы:* находит случаи, о которых не подумал.

**Покрытие кода (coverage)** — доля строк, которые выполнились во время тестов. *Зачем:* увидеть непроверенные места. *Важно:* 100 % покрытия не значит «нет багов» — строка могла выполниться без проверки результата.

**Тест миграций** — проверка, что `alembic upgrade head` строит ту же схему, что описана в моделях. *Зачем:* тесты API создают таблицы из моделей, а сервер — из миграций; без этого теста забытая миграция всплывёт только на проде.

**Матрица доступа** — таблица «роль × эндпоинт → ожидаемый код ответа», прогоняемая одним параметризованным тестом. *Плюсы:* новый эндпоинт без проверки прав сразу заметен. Чужому возвращается 404, а не 403, чтобы нельзя было узнать, что такая семья вообще есть.

**CI (Continuous Integration, непрерывная интеграция)** — автоматический прогон тестов на каждый push и pull request (у нас GitHub Actions). *Плюсы:* сломанный код не попадает в `main`, проверка одинакова для всех и не зависит от ноутбука.

**Матрица CI** — один job, запущенный с разными параметрами (`db: [sqlite, postgres]`). *Плюсы:* без дублирования конфигурации проверяем, что приложение работает на обеих базах.

**Flaky-тест (нестабильный)** — тест, который то проходит, то падает без изменений в коде (гонки, общая база, время). Здесь e2e каждый раз регистрируют нового пользователя и сканируют случайный штрихкод, поэтому не мешают друг другу и идут параллельно.

**AAA (Arrange–Act–Assert)** — структура теста: подготовить данные, выполнить действие, проверить результат. *Плюсы:* тест читается сверху вниз как история.
